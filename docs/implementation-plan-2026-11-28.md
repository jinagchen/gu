# RecallFlow 初赛实施与验收方案

编制于 2026 年 11 月 28 日。代码基线为本地 `main` 的 `f3a611f`，现状取自阶段交付、11 月 28 日问题清单和对应源码。本方案沿用两人 A/B 分工。以下日期为建议的内部交付目标，表中标为赛事截止的日期除外。[前七阶段问题清单](stages-1-7-issue-register.md) · [原验收矩阵](acceptance-matrix.md)

## 1. 交付目标与现状

交付一个运行在本机 Windows x64、NTFS 和 SSD 上的单机向量检索引擎。上层能并发查询、插入和更新。在声明的内存、硬件和负载范围内，静态与动态每个有效评测组都要达到 Recall@10 ≥ 0.85。一次查询使用同一快照，已确认写入在进程重启后可读，持续写入时后台能整理积压，过载时调用者能观察到等待或拒绝。用一个真实 Agent 框架调用示例、独立评测和复现包交付这些能力。[赛题任务书](../赛题任务书-面向Agent记忆的向量检索系统IO优化.md) · [需求基线](requirements.md)

| 已有基础 | 尚需交付的证据 |
| --- | --- |
| FORMAT-1 磁盘图可首建和查询。512 条、16 维静态夹具的历史 Recall@10 为 1.000。 | 当前首建与维护段共用有工作量上限的精确构图。用真实 Engine 在超内存工作集上完成构建、查询和更新。 |
| CLOCK 缓存、同块在途去重、IOCP 和有界下一跳预取已实现。小图驻留时，历史读量从约 102.77 MiB 降至 2 MiB。 | 读量指引擎完成字节。16 MiB 档实际数据驻留约占缓存预算 45.07%，预取的尾延迟收益仍不稳定。 |
| Engine 已实现 `Insert`、`Upsert`、WAL 重放、检查点、后台合并和正常回收。11 月 28 日问题清单记录所选构型 Debug、Release CTest 各 15/15。 | 两个已复现故障仍能阻断维护。真实 `vector_bench` 只接受纯查询，短时维护测试尚不足以给出混合负载 P99 和可持续写入速率。 |

资料发生冲突时，阶段六、七的专项交付和当前代码优先于 README 开头的 11 月 23 日快照。DiskANN 0.6.1 已有独立探针，当前 `vector_build` 的基线为自有 FORMAT-1。项目状态、实验表和演示须标明具体后端、提交与数据规模。[静态交付](stage4-b-completion.md) · [读优化复核](stage5-b-completion.md) · [阶段七交付](stage7-b-completion.md)

## 2. 技术路线

| 路径 | 实施约定 |
| --- | --- |
| 查询 | `Search` 固定快照序号和索引代次，遍历磁盘段并查询增量层，按快照过滤旧版本、按逻辑 ID 去重，用原始向量计算平方 L2，距离并列按 ID 排序。成功返回 `min(K, live_count)` 条，候选预算耗尽且条数不足时返回 `search_incomplete`。 |
| 读取 | 主图通过统一块读取接口，保留同步直读基线。CLOCK 和同块共享减少后端提交，IOCP 提交已知下一跳预取。需求读有预留槽，预取可收缩。合并读取通过同一调度器显式提交后台优先级。 |
| 写入 | 校验 ID、向量和容量，预留空间并分配序号，追加 WAL，`FlushFileBuffers` 成功后发布增量及版本，再返回收据。重复插入返回冲突。追加后结果不确定时标记 `may_have_applied`，停止继续确认写入，重开后核对。 |
| 整理与恢复 | 将已确认的连续前缀落成不可变段，持久化清单并切换 `CURRENT`，重新打开后采纳新视图。只回收已覆盖且没有有效引用的文件。重启从有效清单的检查点重放 WAL，保留尚未落段的尾部。 |
| 调用与评测 | C++20 在引擎所在进程发请求、计时、写原始结果。Python 准备数据，测量结束后生成独立精确答案。上层通过选定框架的公开扩展点调用同一个引擎，并演示写入、查询及错误传播。 |

沿用冻结的 API-1.2、FORMAT-1 与 EVAL-1.1。涉及接口或工件字段变更时，同步更新声明、生产端、消费端及协议示例。[接口契约](interface-contract.md) · [存储协议](storage-protocol.md) · [评测协议](evaluation-protocol.md)

## 4. 实验矩阵与判定

| 批次 | 配置 | 产物与判定 |
| --- | --- | --- |
| 小规模正确性 | 固定种子、平方 L2。静态及动态测试空索引、K=1/10/超有效数、候选不足、插入冲突、多个版本。穿插检查点、长查询和重启。 | 每个结果的 ID、版本、数量、距离、次序正确。确认后可见性用点读和版本探针验证，近似检索用独立快照真值验证。 |
| 超内存与规模 | 以轮次开始时有效原始 float32 向量字节为固定分母，自测 10%、15%、20%。先跑规模阶梯，记录格式、数据哈希、构建耗时及磁盘峰值。例如 100 万条、128 维载荷为 512,000,000 字节，三档为 51,200,000、76,800,000、102,400,000 字节。 | 对基准、引擎及在线后台进程施加同一 Windows Job 提交限额。首建用独立 Job，另报恢复和合并。记录原始峰值、私有提交、工作集、缓存和临时磁盘，披露系统缓存计量范围。示例容量是试算。 |
| 混合与过载 | 查询与写入按 100:0、95:5、80:20，混合写入中插入和更新各半。并发按 1、8、32、64 逐步加压，覆盖多写者、均匀查询、会话热点迁移及突发写。先在 15% 档跑一组 80:20，再向两侧内存档扩展。 | C++ 开放式定速发请求，记录到达、排队、拒绝、超时和排空。静态初值预热 60 秒、测量 300 秒。正式动态组至少 30 分钟且跨三轮合并，每个正式配置至少三次，单列冷启动与稳态。 |
| 读优化与整理消融 | 同步直读、同步加 CLOCK、IOCP 加 CLOCK、再开启有界预取。后台对照关闭维护、只刷盘、固定段预算、停顿触发刷盘，另对比后台读配额开关。各组固定同机、数据、到达轨迹、内存、写入确认语义及相近实测召回。 | 报需求读等待、引擎读取字节、预取被消费及需求到达时已就绪的比例。画查询 P99 对写入速率、积压随时间以及停止投递后的排空曲线。预取无稳定收益时保留关闭配置与负面结果。 |

每组报告查询 QPS、插入和更新各自的确认吞吐、查询与写入 P50/P95/P99、失败和拒绝数、峰值内存、归并前后段数。引擎写放大按 `(WAL + 检查点 + 合并的逻辑文件写字节) / 接受的写入载荷字节` 计算。设备读量或 NAND 写放大只有取得对应设备指标时才填数值。可持续速率需要同时看到实际确认吞吐、读端持续查询、积压走势和排空时间。[评测口径](requirements.md) · [评测协议](evaluation-protocol.md)

完整轮次按约定查询集计算 `recall_at_k.mean`，失败和拒绝计零分。缺工件、排空超时、结果不确定或资源需核查时保留原始结果，按协议登记为无效、不完整或待核查。每次运行保存提交、构建参数、数据及轨迹哈希、有效配置、环境、Job 记录、原始 JSONL、离线答案、验算结论和复现命令。保留同批次的通过和失败配置。[验收矩阵](acceptance-matrix.md)

## 6. 取舍与最终验收

- **截至 12 月 3 日，P0 或动态真值仍失败**，暂停正式吞吐实验。保留能稳定复现的故障、修复记录及小数据演示，优先恢复检查点、续写和快照正确性。
- **规模构建或全量合并超限**，优先投入有界构建或有界合并，公开最大通过规模、最小通过预算和首个失败点。若初赛前只能跑小规模，A-001 及受影响项保留实际状态。
- **积压持续增长或读端压制写端**，逐档降低到达速率，明确背压与拒绝分布，给出最后可持续档和首个过载档。对预取、组提交和高级联合控制，证据充分后再写入贡献清单。
- **提交判定**，A-001 至 A-022 每项记录“通过、失败、未执行、附理由的不适用”之一，关联配置、命令、原始结果和复核角色。报告、代码、视频与提交回执指向同一发布版本。进程终止恢复与实物断电验证分别登记。
- **答辩与赛后**，用一次更新贯穿写入确认、查询新版本、合并、重启读回，再展示相同召回和内存下的读量、P99 与积压曲线。归档发布哈希、工件及评审反馈。按实测瓶颈安排有界分层合并、设备断电试验或更完整的自适应调度。[项目生命周期](../项目全生命周期.md)
